## 已确认的失败原因

两份部署日志均报告：

```text
[deploy] [database] / [launch]
sync public schema failed: code=170000015
modify "submissions" table:
ERROR: column "activity_id" of relation "submissions" contains null values
(SQLSTATE 23502)
```

原项目日志在报错前明确显示 Vite 构建完成、构建流水线成功。失败点是数据库结构同步，不是这一轮前端编译。没有证据表明改为单实例、增加并发额度或清理磁盘能解决这个约束错误。

0.7 的应用迁移原本按“加可空列 → 用原 kind 回填 → 设置非空”执行。但扣子先将开发库的**最终表结构**同步到生产库；新增的 `activity_id NOT NULL` 遇到旧记录就失败，应用尚未启动，自己的回填没有机会运行。开发环境已有新字段且可以运行，并不能证明生产升级会成功。[扣子官方文档](https://docs.coze.cn/guides_integrate_database)说明开发与生产库独立，后续发布同步结构而不复制数据；本次原始日志进一步确认了失败阶段。

此前测试覆盖应用启动迁移，没有覆盖平台先同步表结构的阶段。这是原部署说明遗漏的前置条件，本轮补充复现、预迁移 SQL 和验证记录。现有数据不需要为消除该错误而清空；移除回执也应保留，避免改变学生的提交状态。

## 保留数据的处理顺序

以下是首次排查时准备的通用维护方案。两项目本次已执行并发布，实际执行范围及用户豁免备份的说明见上方“14:13 正式发布与验收完成”；后续部署不应把本次豁免当作默认规则。

1. 分别确认项目、域名、生产数据库、当前运行代码和实际数据来源。特别核对旧站是否仍写 SQLite；若是，先保存实际生产 SQLite，按[存储迁移手册](coze.md#保留旧课堂和作品)核对已有 PostgreSQL，不能直接覆盖或重复导入。
2. 在维护窗口停止所有旧实例和其它提交写入，取得可恢复的完整数据库备份。CSV 只能保存作品，不包含密码、会话和元数据，不能替代完整备份。原项目数据库总览显示可溯回时间为 0 小时，本轮没有验证可用恢复点；需要先落实备份。
3. 在目标项目的“数据库 → 生产环境 → SQL 查询”运行[只读预检](sql/coze-activity-id-preflight.sql)，保存数量和表结构。重新核对后再维护，不把本页的历史计数硬编码为现状。
4. 备份和停写已落实后，经维护负责人确认，完整执行[预迁移 SQL](sql/coze-activity-id-premigration.sql)。它只增加 `activity_id`、为 NULL 回填原 `kind`、设置非空；不改正文、删除标记、课堂 ID、密码、会话、旧唯一约束或旧类型约束。全文件在一个事务和同一连接中执行，锁等待 5 秒、语句超时 30 秒；报错后先 `ROLLBACK` 再排查，不能从中间挑语句重试。
5. 再次运行只读预检，确认总数／可见数／回执数不变且 `activity_id:NO`。随后发布选定的新代码，让平台同步其余结构，应用完成唯一索引、类型约束和活动配置升级。两个项目各用自己的代码与数据库；不把开发数据覆盖生产。
6. 在正式域名确认实际发布版本、PostgreSQL / polling、原密码登录与刷新、固定学生链接、原提交及回执、新增同类型活动与逐题结果门槛。通过后再开放课堂，记录部署提交及验收结果。

**预迁移提交后，旧代码因缺少 activity_id 不能继续提交。** 所以此 SQL 不能在上课中执行，也不能作为自动构建步骤。新旧实例混用仍不受支持。若发布失败，保持停写并排查；需要回退时恢复完整备份和匹配旧代码，不能仅回退 Git。

## 其它方案的边界

- 开发侧改为可空列也能避开本次 NOT NULL 冲突，但需要同时修改建表和启动迁移、验证所有写入及唯一性、测试旧新版本交接；仅在数据库面板取消非空，下一次应用启动仍会加回来。本轮没有实施这种架构调整。
- 没有验证到可关闭平台 schema 同步的可靠设置，不能把它当成已可用方案。
- 清空 submissions 会丢作品或回执，本轮没有采取。两个项目的身份、数据、域名和部署记录独立，不能互相替代。
